Vireo vs llama.cpp on a laptop GPU, the Mac's 14 November benchmark

The Mac's benchmark of 14 November rebuilt for this laptop: Gemma 4 E2B and E4B and Qwen 3.5 4B and 9B at Q4, both engines through their servers, one run each, with a long prompt as large as the 8 GB GPU holds (~15–26K tokens). Vireo, as shipped, writes the Gemmas' replies 28–45% faster than llama.cpp, thanks to its guesses, and is level on the Qwens. It reads every long prompt more slowly (−25% to −12%, median −19%), so its first token after one comes later, and it uses more of the GPU's memory. The agent tasks are mixed: faster on the Gemmas' tool task, slower on the Qwens'. It got 15 of 20 scored tasks right, against llama.cpp's 18.

Where Vireo is ahead and where it is behind

  • Writing: through its server Vireo takes guesses from the chat and, for the Gemmas, from Google's draft models, and checks them in one pass; llama.cpp writes one token at a time. So on the Gemmas Vireo writes a short reply +28% and +33% faster, and after the long prompt +42% and +45% (that answer quotes the planted facts, which the chat's guesses copy). The Qwens have no draft model: level on a short reply (−1%, −1%), −8% and +2% after the long prompt.
  • Reading: behind on every long prompt, −25% to −12% (Qwen 3.5 9B the furthest behind), and so behind on the first token after it (−25% to −11%). At ~3K tokens: level on the Gemmas (+4%, +1%), behind on the Qwens (−18%, −22%). This matches the morning's measurement with no server and no drafting (78–84% of llama.cpp at the long prompt).
  • Agent tasks: Vireo finishes the tool task faster on the Gemmas (+17%, +41%) and slower on the Qwens (−42%, −34%). It is slower on the skill task on three of four (−31% to +2%). Vireo's own instructions and tools make its task prompts 1,500–2,100 tokens against llama.cpp's 350–850. On the Qwens Vireo reads them all again (none of an earlier chat's start is kept), and it writes more: a summary after the answer, and each tool call to a grammar. The long tool task compares on the Gemmas only (0%, +8%): both Qwens failed it on Vireo, and Qwen 3.5 4B on llama.cpp too.
  • Memory: Vireo uses more of the GPU on all four (−29% to −8%): 2.9 GB against 2.3 GB on E2B, 5.6 GB against 4.0 GB on E4B, 6.7 GB against 6.2 GB on Qwen 3.5 9B. vireo-server also holds the Gemmas' draft models and its skill picker's sessions. This is the whole GPU's memory, Windows' share included, not a process's peak.
  • Answers: Vireo 15 of 20, llama.cpp 18. Both engines got long recall and every multiturn turn right on all four models. Vireo's misses are Gemma 4 E2B's tool, skill and long tool tasks, and both Qwens' long tool task. llama.cpp missed E2B's long tool task (the same wrong path) and Qwen 3.5 4B's (the same runaway call). The Mac had Vireo's Gemma 4 E2B wrong on the tool and skill tasks too.

How this run differs from the Mac's

  • Q4, not Q6: Google's QAT Q4_0 for the Gemmas, unsloth's Q4_K_M for the Qwens, the same GGUF files for both engines. The Mac ran all eight test models at Q6; this laptop has room for the four small ones only.
  • About 32K of context, not 131,072: vireo-server sizes its context to the GPU memory free: 32,768 tokens for three models and 21,504 for Qwen 3.5 9B, which fills the 8 GB GPU. llama-server got the same context plus 2,048. The long prompt is long.txt cut to fit, so it is 26,306 tokens for the Gemmas, 24,736 for Qwen 3.5 4B and 15,310 for Qwen 3.5 9B (by llama.cpp's count). It stands in for the Mac's ~32K row; there are no 96K or 128K rows, and so five scored tasks, not six.
  • No mlx-vlm: it runs on Apple's GPUs only, so Vireo is compared with llama.cpp alone.
  • Rebuilt prompts and tasks: the Mac's harness (bench-2026-11-13) was never pushed. bench_tasks.py rebuilds its workloads from the Mac's report: the same three prompt files (prompts-mac/), but its own question, planted facts, multiturn chat, tool, skill and log tasks. Times are not comparable with the Mac's, only the comparison within this page.
  • GPU memory is the whole GPU's in use (nvidia-smi) after the long prompt, read once with the server still loaded. The Mac's is the server process's peak.
  • The long tool task's log is about 55% of the context (~18K tokens for three models, ~11K for Qwen 3.5 9B), against the Mac's ~20K.

What failed or looked odd

  1. Qwen 3.5 4B and 9B · Vireo · long tool task: "A tool call ran too long" after 62.8 s and 86.8 s, with no answer. With the server's call debugging on, a re-run shows Qwen 3.5 4B counting the log's error lines inside a calculate call, sum([1, 2, 3, … 128, …, until the engine's 4,096-token limit for one call stops it. Shown as missing. The Mac's Qwen 3.8 27B hit the same limit on 13 November.
  2. Qwen 3.5 4B · llama.cpp · long tool task: HTTP 500, "Failed to parse tool call arguments as JSON … missing closing quote". The same runaway calculate call, sum([1, 1, 1, …, cut off by the 512-token cap. Shown as missing. Qwen 3.5 9B on llama.cpp passed a list of names to calculate, then got the answer right anyway.
  3. Gemma 4 E2B · both engines · long tool task: it listed services, then asked for inventory-sync.conf without the folder, was told the file doesn't exist, and gave up. Wrong on both; their times are shown.
  4. Gemma 4 E2B · Vireo · tool and skill tasks: the tool task added up the quarters without calculate and got $26,149.25 (right: $26,742.25). The skill task gave the right total, 78, and said the report was saved, but never called write_file. llama.cpp got both right. The Mac's Vireo E2B also missed both.
  5. Unasked tool calls on Vireo (its own tools are offered with every chat): Gemma 4 E2B called get_current_datetime during the short reply; Qwen 3.5 4B called remember in the multiturn chat (refused at once by the harness) and get_current_datetime; Qwen 3.5 9B took the summarize-document skill for the tool task. All of those answers were still right.
  6. The harness, fixed during the run (the first two runs are in superseded-run1.jsonl and superseded-run2.jsonl): llama.cpp's first-token time was taken when its first request had finished, so it equalled the whole reply's time; the long tool task's log was sized at 3.2 characters a token, when it tokenizes at ~1.9, so it filled nearly the whole context ("The message is 21276 tokens, too long for this server's 21504-token chats" on Qwen 3.5 9B); and Vireo's stream errors, its tool calls' arguments and its server log were not kept. Every number on this page is from the third run, after the fixes.
  7. Vireo's agent-task speeds come from one server line for the whole task (llama.cpp's are summed over its round trips), so the tasks are compared by their wall time only, as on the Mac.
  8. One run each: a difference of a few percent is within noise. The speed check before each run held (6,283–6,343 tokens/s reading, 86.7–89.0 writing), and run 3's reading and writing speeds were within 7% of run 2's (Gemma 4 E2B reading ~3K the most; the harness hadn't changed those workloads).
