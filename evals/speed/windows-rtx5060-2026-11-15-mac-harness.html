Vireo vs llama.cpp on a laptop GPU, with the Mac's own harness

The Mac's harness of 13–14 November (bench-2026-11-13/bench.py), run unchanged on this laptop but for its paths, memory reading and contexts, on the merged build (PR #167): Gemma 4 E2B and E4B and Qwen 3.5 4B and 9B at Q4, both engines through their servers, one run each, the Mac's prompts whole except Qwen 3.5 9B's long tool log. Vireo finishes the tool task faster on all four (+5% to +125%) and the skill task on three, and gets the same answers right as on the Mac. It reads every long prompt more slowly (−21% to −15%), so its first token after one comes later and the long tool task takes longer, and it uses more of the GPU's memory. On the Mac the same harness has Vireo reading faster. The merge itself: both Qwens now finish the long tool task that failed before, and the Gemmas' tool and skill tasks are quicker.

Where Vireo is ahead and where it is behind

  • Agent tasks: the tool task is faster on all four (+5% to +125%; Gemma 4 E4B +125%, where llama.cpp took 14.4 s and got it wrong), the skill task on three (−25% to +71%; slower on Qwen 3.5 9B, 24.0 s against 18.1 s, with 17 tool calls against 8). The long tool task is slower on all four (−26% to −2%): reading its ~56K-token log (~29K for Qwen 3.5 9B) is most of it, and Vireo reads more slowly. The Mac is ahead on all three task times (+44% to +72%, +54% to +227%, +39% to +105%).
  • Reading: behind on every ~32K prompt, −21% to −15%, and so on the first token after it (−21% to −15%). At ~3K tokens: level or ahead on the Gemmas (+8%, 0%), behind on the Qwens (−19%, −23%). On the Mac Vireo reads the same prompts +35% to +60% faster than llama.cpp: reading long prompts is where the CUDA engine is behind.
  • Writing: after the ~32K prompt, ahead on the Gemmas (+12%, +4%) and behind on the Qwens (−13%, −5%). A short reply: ahead on Gemma 4 E4B (+27%), behind on the other three (−10%, −8%, −10%). Gemma 4 E2B's is one reply that took fewer of the draft model's guesses: re-checked, it wrote at 190–198 tokens/s, ahead. The Qwens have no draft model on Windows. The Mac is ahead on all four (+3% to +15%).
  • Memory: Vireo uses more of the GPU on all four (−42% to −15%): 7.5 GB against 4.3 on Gemma 4 E4B, 3.5 against 2.4 on E2B. Vireo sets aside the whole context's caches when it starts (3.8 GB for Gemma 4 E4B at 65,536 tokens, by its log) and also holds the Gemmas' draft models and its skill picker; llama.cpp keeps the Gemmas' sliding-window layers short. The Mac's process peaks, 128K prompt included: −20% to +1%.
  • Answers: Vireo 16 of 20, llama.cpp 15. Vireo's misses are exactly the Mac's, model for model: Gemma 4 E2B's tool and skill tasks, the skill task on E4B and Qwen 3.5 4B. Every model on both engines got long recall and all eight multiturn turns right, and only Qwen 3.5 9B got the skill task right (on both engines).

How this run differs from the Mac's

  • Q4, not Q6: Google's QAT Q4_0 for the Gemmas, unsloth's Q4_K_M for the Qwens, the same GGUF files for both engines. The Mac ran Q6.
  • Context, 65,536 or 32,768, not 131,072: vireo-server's own choice stops at 32,768, and the Mac's ~32K prompt is 33,797 tokens on Vireo for the Gemmas and its long tool prompt ~57K. So both engines were given 65,536 for Gemma 4 E2B, E4B and Qwen 3.5 4B, checked with Windows' GPU counters to fit without spilling into the PC's memory (context-probe.jsonl). Qwen 3.5 9B spilled at 59,392 on Vireo (its long tool prompt read at 145 tokens/s), so it ran at 32,768: its ~32K prompt whole (31,144 tokens), its long tool log cut to the first half (43,922 of 87,876 characters, at a line's end; inventory-sync still logs the most ERROR lines, 24 against card-reader's 13), for both engines. Every other prompt is the Mac's, whole.
  • No 96K or 128K rows, no mlx-vlm: an 8 GB GPU can't hold them, and mlx-vlm runs on Apple's GPUs only. So five scored tasks, not six, and llama.cpp is the only other engine. Vireo without guesses (the harness's vireo-plain) was left out: on Windows it only turns off the Gemmas' draft models and the chat's guesses, measured on their own in PR #166.
  • GPU memory, not the process's peak: the whole GPU's in use (nvidia-smi), read after each workload, Windows' own ~0.4 GB included; the highest is shown. The Mac's is the server process's peak.
  • Harness changes, Windows only: the Q4 files, llama.cpp b12262's llama-server.exe and the contexts; the folder's path written with forward slashes in the questions (a model copying C:\Users\twitc\… into a tool call can turn \t and \n into a tab and a new line: llama.cpp's skill task on Gemma 4 E4B failed five reads that way in the smoke test); Python's UTF-8 mode. The Mac runs the same file unchanged.
  • The Mac's columns are its run of the same harness on the same four models (results-q6-128k.jsonl, M5 Max): a different machine, quantization and context, for the direction of each difference, not its size.

What failed or looked odd

  1. Vireo · long tool task · no tool call: on both Gemmas and Qwen 3.5 9B Vireo named inventory-sync from the log and answered without reading the README or suppliers.md, saying it had checked them (Gemma 4 E4B named suppliers that aren't in the file). The Mac's rows show the same for the same three models. The Mac's scoring checks the component's name only, so these count as right.
  2. llama.cpp · Gemma 4 E2B · tool task: scored right by the Mac's rule (the year's total, $26,742.25, appears) but wrong: it gave every quarter $26,742.25 and the year $106,969.
  3. Skill task: only Qwen 3.5 9B got 78 hours, on both engines. The others summed the wrong numbers (Qwen 3.5 4B on Vireo added 14 of the notes' entries to 73); llama.cpp's Gemma 4 E4B gave 84, Vireo's 97. On the Mac the same models missed it the same way.
  4. Qwen 3.5 9B · context: at 59,392 tokens Vireo's caches spilled into the PC's memory (Windows' shared GPU memory 0.51 GB; reading 145 tokens/s), so it ran at 32,768 with its long tool log cut. llama.cpp would have held 59,392 (6.9 GB, no spill).
  5. Gemma 4 E2B · one-off speeds: the Mac harness's short reply on Vireo (144.7 tokens/s), and the rebuilt benchmark's after-merge ~3K read (10,287) and short reply (175.0). Re-run, 190–198, 15,773 and 200.0. The rows are kept as measured; the re-checks are in RECHECKS.md.
  6. Qwen 3.5 4B · llama.cpp · rebuilt benchmark's long tool task: still HTTP 500 after the merge (llama.cpp didn't change): its runaway calculate call cut off at 512 tokens. In the Mac harness, with its 512-token cap and a larger log, it finished.
  7. Gemma 4 E4B · Vireo · GPU memory: 7.5 of 8 GB in use at 65,536 tokens, the most of any row; Windows' counters showed no spill.
