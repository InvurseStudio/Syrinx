Where Vireo is ahead and where it is behind

  • Memory: the Gemmas' sliding-window layers now keep only their window, so Vireo's Gemma servers load at 2.5 GB (E2B, was 3.3) and 4.7 GB (E4B, was 7.2). Vireo still uses more than llama.cpp on all four (−22% to −14%; this morning −42% to −15%): it sets aside the whole context's caches for the other layers when it starts, and holds the Gemmas' draft models and its skill picker. The Qwens have no sliding-window layers and didn't change.
  • Reading: still behind llama.cpp on every ~32K prompt (−19% to −9%; this morning −21% to −15%), and so on the first token after it (−18% to −12%). At ~3K tokens the run's rows put Vireo behind on all four (−23% to −6%), but the Gemmas' two were one-offs: re-run, they read at the morning's speeds (17,017 and 6,249 and 6,253 tokens/s; RECHECKS.md), level with or ahead of llama.cpp.
  • Agent tasks: the tool task is faster than llama.cpp's on three (−1% to +67%), the skill task on two (−21% to +71%); the long tool task is slower on all four (−21% to −1%), mostly reading its ~56K-token log. llama.cpp's own task times moved between its two runs because its answers did: Gemma 4 E4B's tool task took 14.4 s this morning and got it wrong, 10.0 s now and got it right.
  • Writing: after the ~32K prompt level overall (−12% to +5%); a short reply −10% to +18%. Writing wasn't touched by the changes; its moves are one reply each (re-checked for Gemma 4 E4B: 115.1 and 115.2 tokens/s).
  • Answers: Vireo 16 of 20 here, as this morning (16); llama.cpp 17 (15 this morning, with the same program: its answers vary from run to run).

Today's three changes

  • 1. Qwen's saved state at the system turn's end (vireo-server, Kept::turn): when Qwen reads a system turn, its DeltaNet layers are saved a few tokens before the turn's end, so the next chat with the same instructions and tools starts from there. Before, the one saved state was where the first two chats parted. In this harness each Qwen task kept the start it shares with the chat before it (1,477 tokens on Qwen 3.5 4B) or none (the tool and skill tasks' system turns differ from the chats before them), so it shows in the eval, where every case shares one system turn.
  • 2. Sliding-window rings on CUDA (attention_ring, ring_row in vireo.cu; gemma4_cuda.rs): a sliding-window layer keeps its window and a batch's new positions, position p at row p mod ring, as the Mac has done. The Gemmas' GPU memory drops; the cost is that a ring which has gone round can't go back, so after a prompt longer than the ring the next chat reads its instructions and tools again (0 kept), as on the Mac.
  • 3. The prompt attention kernel (q_rows_to_half, attention_mma and a _short set for batches up to 64 tokens): a batch's queries are turned to f16 where they lie instead of being copied into each block's shared memory, which frees that memory for larger blocks on batches over 64 tokens. Long prompts read faster; Gpu::attention now leaves a batch's queries in f16.

What failed or looked odd

  1. Gemma · Vireo · instructions read again: after any prompt longer than a sliding-window ring, the next chat keeps 0 tokens: Vireo's 1,301 tokens of instructions and tools are read again (tool task 836 → 1,721 tokens on E2B). This is the Mac's behaviour too (its rows show 0 kept after the long prompt), a cost of the rings; a saved copy of the rings at the system turn's end would avoid it.
  2. Gemma · eval a little slower: the rings' cost shows in the eval, where cases follow each other on one server: the Gemmas read 15,887 → 30,201 and 21,980 → 39,241 tokens (before → after), and Gemma 4 E4B's 43 cases took 51 → 54 s. The Qwens were faster (128 → 103 s, 196 → 161 s).
  3. Gemma · Vireo · one-off ~3K reads: the run's ~3K-token reads were 13,927 (E2B) and 5,888 (E4B) tokens/s; re-run, 17,017 and 6,249 and 6,253, as this morning. Gemma 4 E4B's short reply (104.3 tokens/s) re-checked at 115.1 and 115.2. Rows kept as measured (RECHECKS.md).
  4. Qwen · saved state not used in this harness: the tool and skill tasks read from 0 on both builds: their system turns (with the harness's client tools) differ from the chats before them, so neither saved state matches. The change shows in the eval instead.
  5. llama.cpp's answers vary between runs: the same program scored 15 this morning and 17 now: Gemma 4 E4B's and Qwen 3.5 4B's tool tasks are now right, Gemma 4 E2B's skill task gave 88 hours (63 this morning).
  6. Vireo · answers differ by rounding: greedy replies changed in places on both engines' runs; on Vireo the attention kernel's new blocks add up in a different order, so a close choice between two tokens can tip (Gemma 4 E2B's tool task gave Q3 as 6,496.75, 4,317.75 this morning, wrong both times).
  7. Eval · four cases changed: Gemma 4 E2B's skill-review and office-policy and Qwen 3.5 4B's office-invoices now pass; Gemma 4 E4B's calc-tip now fails because it did the sum itself, with the right result. All four tipped on close choices; none is a wrong answer caused by the changes.
